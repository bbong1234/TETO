## 2. 已确认的核心事实

以下事实已在实现总结报告中整理，并经验收验证报告做代码静态核对：

1. QuickInput 主链为 `POST /api/v2/inputs`
2. QuickInput 不回退 `POST /api/v2/parse`
3. Ingest V2 关闭时前端阻断、服务端 403
4. 前端存在 session 会话卡机制（`client_session_id`、`session:${id}`）
5. `saved` 仅类型存在，当前无实际赋值路径；成功入库后会话卡移除而非变为 `saved`
6. `failed` 会话卡存在，但 `Input` / `InputUnit` 的 `failed` 主链不写表状态
7. 后端输入态为 `inputs` + `input_units`
8. `records` 为正式态
9. `PendingQuestion` / `clarify_class` 驱动澄清 UI
10. `split` / `keep_single` / `cancel` / `defer` / `skip` / `answer` 语义已按源码整理
11. record 质量字段写入矩阵已明确（直入库 / answer / skip）
12. `createRecordSafely` 负责 `records` 创建，不负责 `input_unit` 生命周期
13. `selectedDate` / `client_time` 存在已知时间解析 gap
14. 10 阶段 Agent Pipeline 不属于 QuickInput 当前真实主链

## 3. 已知 gap

下列 gap **仅记录**，**不在本轮修复**。

### 3.1 selectedDate 与 classify 日期不一致

- QuickInput 发送 `metadata.date`
- 当前未发送 `body.date`
- `inputs/route.ts` 使用 `body.date || server today` 传入 `ingestFull` / `classifyInput`
- `client_time` 当前仅写入 metadata，服务端未参与解析
- 影响相对时间解析（`occurred_at`、`time_anchor_date` 可能与 UI 所选日不一致）

### 3.2 LLM 导致验收触发不稳定

- 普通直入库、字段澄清、复合句确认依赖 `classifyInput` / LLM 返回
- 同一自然语言输入未必稳定触发同一分支
- 后续运行时验收需要固定输入集或 mock

### 3.3 复合句确认不保证稳定出现

- 多事件输入可能直接多 unit 晋升
- 也可能触发 `compound_confirm`
- 取决于当前 classify 结果

### 3.4 端到端运行验收未完成

- UI 未手测
- API 未稳定连通
- DB 未查询
- trace / debug 未验证
- 因此只能称为**静态验收通过**，不能称为端到端实测通过

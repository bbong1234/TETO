## 版本信息

- 版本号：1.7
- 版本名称：时间记录主线重构版
- 核心目标：让时间记录主流程跑通
- 开发原则：复用 1.6 能力，重构主入口，不盲目推倒重来

---

# 一、1.7 核心定位

## 1.1 一句话定义

> **TETO 1.7 是时间记录主线重构版本，它把主入口从"QuickInput/AI解析"改为"当前事项/时间切换"，让用户能低阻力地开始、切换、归类和回看自己的时间。**

---

## 1.2 核心问题

1.7 要解决的核心问题是：

> **用户每天真正高频的问题不是"这句话能不能被 AI 结构化"，而是"我现在在干什么、我刚才切换到了什么、今天我到底做了多久"。**

---

## 1.3 产品主线变化

### 旧主线（1.6）

```
QuickInput → AI解析 → 澄清 → records
```

### 新主线（1.7）

```
当前事项 → 开始/切换/结束 → 自动形成时间记录 → 分类/项目归属 → 今日时间线 → 今日统计
```

---

## 1.4 1.7 的边界

### 1.7 做什么

```
当前事项 Current Activity
开始/切换/结束行为
快速切换面板
今日时间线
今日统计
分类/项目归属
记录内笔记
项目归档
空白时间识别
```

### 1.7 不做什么

```

学习进度预测
日记/复盘输入
24 小时完整时间结构分析
问题记录/观察日志/第二大脑
能力缺口分析
行业定位分析
财务管理
番茄钟
四象限
复杂 GTD
10阶段 Pipeline 接入 QuickInput
Debug Trace 页面
AI洞察润色强化
复杂目标引擎深化
```

# 三、数据模型方案

## 3.1 核心原则

1. **尽量复用 1.6 已有表和字段**
2. **最小新增字段**
3. **不修改 sql 文件夹里的已有文件**
4. **如果必须新增字段，先提出理由和迁移方案**

---

## 3.2 records 表复用分析

### 3.2.1 已有字段

根据 1.6 功能说明，records 表已有：

```

occurred_at_end

```

### 3.2.2 字段复用方案

#### 当前事项表达

**方案：用 status 表达进行中状态**

```
status = 'active' 或 'ongoing' → 进行中
status = 'completed' → 已完成
status = 'cancelled' → 已取消
```

需要确认：

- 当前 status 枚举是否已有 'active' 或 'ongoing'
- 如果没有，需要新增枚举值

#### 开始时间

**复用：occurred\_at**

#### 结束时间

**复用：occurred\_at\_end**

#### 持续时长

**复用：duration\_minutes**

#### 项目归属

**复用：item\_id**

#### 内容

**复用：content 或 main\_text**

#### 笔记

**方案 1：复用现有字段**

- 如果 records 表已有 notes 或 remarks 字段，直接复用

**方案 2：新增字段**

- 如果没有，需要新增 notes 字段（text 类型）

**方案 3：独立 notes 表**

- 如果需要支持一条记录多条笔记，建立独立 notes 表
- notes 表结构：

  ```
  id
  user_id
  record_id
  content
  created_at
  updated_at
  ```

---

### 3.2.3 需要确认的问题

1. **当前 status 枚举值是什么？**

   - 是否已有 'active' / 'ongoing'？
   - 是否已有 'completed'？
   - 是否已有 'cancelled'？
2. **当前是否已有 notes 或 remarks 字段？**

   - 如果有，字段类型是什么？
   - 如果没有，是否需要新增？
3. **当前 item\_id 是否可以为 null？**

   - 因为有些记录可能只有分类，没有项目
4. **当前是否已有 category / subcategory 字段？**

   - 如果没有，如何表达分类？
   - 是否用 tags？
   - 是否需要新增字段？

---

## 3.3 分类体系方案

### 方案 1：复用 tags

**优点：**

- 不需要新增表
- 不需要新增字段
- 灵活

**缺点：**

- tags 是数组，不适合表达层级关系
- 不适合表达大类/子类
- 统计时需要解析 tags

---

### 方案 2：新增 category / subcategory 字段

**在 records 表新增：**

```
category VARCHAR(50)
subcategory VARCHAR(50)
```

**优点：**

- 简单直接
- 统计方便
- 层级清晰

**缺点：**

- 需要数据库迁移
- 需要修改 records 表

---

### 方案 3：独立 categories 表

**新建 categories 表：**

```
CREATE TABLE categories (
  id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
  user_id UUID NOT NULL REFERENCES auth.users(id),
  name VARCHAR(100) NOT NULL,
  parent_id UUID REFERENCES categories(id),
  type VARCHAR(20) NOT NULL, -- 'category' or 'subcategory'
  created_at TIMESTAMPTZ DEFAULT NOW(),
  updated_at TIMESTAMPTZ DEFAULT NOW()
);
```

**在 records 表新增：**

```
category_id UUID REFERENCES categories(id)
subcategory_id UUID REFERENCES categories(id)
```

**优点：**

- 分类可管理
- 支持用户自定义分类
- 支持层级关系

**缺点：**

- 需要新增表
- 需要数据库迁移
- 复杂度增加

---

### 推荐方案

**推荐方案 2：新增 category / subcategory 字段**

理由：

- 简单直接
- 统计方便
- 1.7 先用固定分类，不需要复杂管理
- 后续如果需要用户自定义分类，再升级为方案 3

## 3.5 当前事项存储方案

### 方案 1：用 records 表的 status

**逻辑：**

- 一个用户同一时间只能有一条 status \= 'active' 的 record
- 查询当前事项：`SELECT * FROM records WHERE user_id = ? AND status = 'active'`

**优点：**

- 不需要新增表
- 不需要新增字段
- 逻辑简单

**缺点：**

- 需要保证同一用户只有一条 active 记录
- 需要在切换时先结束上一条

---

### 方案 2：新增 current\_activity 表

**新建 current\_activity 表：**

```
CREATE TABLE current_activity (
  id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
  user_id UUID NOT NULL REFERENCES auth.users(id) UNIQUE,
  record_id UUID NOT NULL REFERENCES records(id),
  started_at TIMESTAMPTZ NOT NULL,
  created_at TIMESTAMPTZ DEFAULT NOW(),
  updated_at TIMESTAMPTZ DEFAULT NOW()
);
```

**优点：**

- 明确表达当前事项
- 查询快
- 不依赖 records.status

**缺点：**

- 需要新增表
- 需要维护两张表的一致性

---

### 推荐方案

**推荐方案 1：用 records 表的 status**

理由：

- 简单
- 不需要新增表
- 当前事项本质上就是一条未结束的 record

# 五、核心交互流程

## 5.1 开始一件事

```
用户点击"开始一件事"
  ↓
弹出选择面板
  ↓
用户选择大类（必选）
  ↓
用户选择子类（可选）
  ↓
用户选择项目（可选）
  ↓
用户输入事项内容（可选，可为空）
  ↓
用户点击确认
  ↓
系统创建一条记录：
  status = 'active'
  occurred_at = 当前时间
  occurred_at_end = null
  duration_minutes = null
  category = 选择的大类
  subcategory = 选择的子类
  item_id = 选择的项目
  content = 用户输入的内容
  ↓
首页当前事项卡片更新
  ↓
计时器开始
```

---

## 5.2 切换到下一件事

```
用户点击"切换"
  ↓
弹出选择面板（同"开始一件事"）
  ↓
用户完成选择后点击确认
  ↓
系统执行两步操作（原子操作，保证一致性）：

【第一步：结束上一条记录】
  上一条记录：
  status = 'completed'
  occurred_at_end = 当前时间
  duration_minutes = (当前时间 - occurred_at) / 60

【第二步：创建新的进行中记录】
  status = 'active'
  occurred_at = 当前时间
  occurred_at_end = null
  duration_minutes = null
  category = 选择的大类
  subcategory = 选择的子类
  item_id = 选择的项目
  content = 用户输入的内容
  ↓
首页当前事项卡片更新
  ↓
时间线更新（上一条出现在时间线，新的进行中显示在顶部）
  ↓
今日统计更新
```

---

# 七、技术实现要点

## 7.1 一个用户只能有一条 active 记录

**数据库层保障：**

```
-- 唯一索引：同一用户只能有一条 active 记录
CREATE UNIQUE INDEX idx_records_user_active
  ON records(user_id)
  WHERE status = 'active';
```

**应用层保障：**

- start 接口前置校验，如已有 active 记录则返回 400 + 错误信息
- switch 接口用事务保证原子性

---

## 7.2 switch 接口原子性

```
BEGIN;
  -- 结束上一条
  UPDATE records
    SET status = 'completed',
        occurred_at_end = $switched_at,
        duration_minutes = EXTRACT(EPOCH FROM ($switched_at - occurred_at)) / 60
    WHERE user_id = $user_id AND status = 'active';

  -- 创建新的
  INSERT INTO records (
    user_id, category, subcategory, item_id, content,
    occurred_at, status
  ) VALUES (
    $user_id, $category, $subcategory, $item_id, $content,
    $switched_at, 'active'
  );
COMMIT;
```

---

## 7.3 空白时间计算

```
1. 获取今天的所有 completed 记录，按 occurred_at 升序
2. 获取第一条记录的 occurred_at 作为"今天第一次记录时间"
3. 获取当前 active 记录（如有）
4. 遍历相邻记录，计算 gap：
   gap = 下一条记录的 occurred_at - 上一条记录的 occurred_at_end
   如果 gap > 0，则该时间段为空白
5. 返回空白时间段列表
```

---

## 7.4 计时器实现

**方案：前端实时计算**

```
elapsed_minutes = (当前时间 - record.occurred_at) / 60
```

每秒更新显示，不需要服务端定时任务。

## 8.5 推荐的第一步

**第一步：确认现有数据库字段，写出迁移脚本**

具体做法：

1. 检查 `records` 表现有 `status` 枚举，确认是否有 `active`
2. 确认是否需要新增 `category` / `subcategory` / `notes` 字段
3. 检查 `items` 表现有 `status` 枚举，确认是否有 `archived`
4. 写出最小迁移脚本
5. 确认后执行

**为什么第一步是数据库确认而不是前端组件？**

```
因为所有 API 和前端组件都依赖数据模型。
数据模型没确定，上层都是空的。
```
